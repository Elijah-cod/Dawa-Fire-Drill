# Phase 3 frontend

In progress. All data is synthetic; model outputs are illustrative and unvalidated.

The local demo proxy must obtain its server-only synthetic token from its environment, never expose it to the browser, and query the authenticated backend demo-capabilities endpoint before presenting role switching. Development fixtures and the later deployment sign-in design remain outstanding.

The authenticated backend demo session endpoint returns the validated role and scope, not the bearer token. A rejected or missing token must be presented as an unavailable session; no production sign-in flow has been designed.

The initial same-origin client covers session, capability and national overview reads with OpenAPI-generated response types. The page uses the controlled-session provider and the typed proxy client in demo mode, or synthetic fixtures in development. The remaining API operations still need typed clients.

The current work is an incomplete national-view scaffold: the schematic grid, an adapter-driven `AuthProvider`, a local/staging proxy, and backend-generated synthetic fixtures for four roles are present. The mock currently covers only the overview and Kisumu run. The proxy is off unless server-only demo settings are supplied and refuses production. Staging must be protected by an external access control because the demo proxy uses a privileged synthetic identity. The app has no sign-in screen; a real deployment sign-in and session design requires separate approval.

The scaffold has not passed a screen review. Its national copy and persistent synthetic notice now support English and Swahili, and theme controls offer system, light, and dark. A mobile full-screen schematic sheet and county list are present. Compared with the approved design, it still lacks bottom navigation, complete role views and all required states, and the remaining screens. The national scaffold and its mobile sheet passed initial axe checks with no serious or critical violations on the four viewport projects. Visual regression baselines, full keyboard journeys, offline queue, Lighthouse budgets and the complete real-backend demo remain outstanding.

### Guided demo

“Try the 3-minute demo” in the top bar starts a seven-step guided walk: national overview, Kisumu pilot, 40% shock, first stockout, funding trace, ranked fix, and bin-card capture. The step is kept in the URL (`?tour=<step>`) so it survives navigation and reloads. Each step shows a short caption in a bottom sheet on mobile and a corner card from 768 px, moves focus to the caption heading, scrolls to and outlines the relevant section, and offers Back, Next step (skips ahead without waiting) and Exit demo; Escape exits. The demo only navigates and scrolls, applies the 40% shock, presses Rank once at the default 100 KES ceiling, and switches the demo role to facility for the capture step; every result shown comes from the normal screens. The Swahili captions (`tour*` strings) need native-speaker review.

### Bin-card capture (online only)

The facility in-charge view has a “Capture a bin card” section. The user must state the card is synthetic, choose a PNG, JPEG or WebP photo up to 5 MB (camera on mobile), and press “Read the card”. The backend validates and strips the image and extracts fields only if a provider is configured; the local stack has none, so it returns empty fields and the screen asks for manual entry. The photo preview sits beside four editable fields (commodity, opening and closing balance, record date); empty or unclear values are highlighted. “Review and save” opens the required confirmation, “Review every field against the photo. Save these values to this synthetic facility?”, with “Go back” and “Confirm and save”. Nothing is saved before that confirmation. The same photo reuses its idempotency key on retry.

Deviations from `docs/design/screens.md`, at the user's direction for 2026-11-08: there is no offline queue (offline shows “Go online to upload a bin card.” and disables upload), and the read-error copy says “Retake the photo and try again” because manual entry needs a created capture. No real LLM provider has been called; extraction quality is untested. Capture Swahili strings (`capture*`) need native-speaker review.

### Budget-limited ranked fixes

The ranked-fix panel now builds one synthetic transfer (10 KES) and one emergency delivery (50 KES) for each planted route that targets an early shock-caused stockout (four with generator version 5, seed 42), asks OR-Tools to maximize modeled days deferred within the ceiling (no minimum-benefit target), and starts at 30 KES so the cut line is visible. On the Kisumu path, an action left out only because it no longer fits the remaining budget is labeled `remaining_budget_exceeded` (“Not funded: it does not fit in the remaining budget.”); the generic optimizer's reasons are unchanged. New or changed Swahili strings (`rankTargets`, `rankRemainingBudget`, `rankCandidateAssumptions`, `rankTransferUnavailable`) need native-speaker review.

The facility map and panel add “Already short before the shock” for facilities in the run's pre-shock or no-shock stockouts, so Critical at 0% is explained. The Swahili label (`alreadyShort`) and the legend's horizon note need native-speaker review.

Map cluster labels use short status names (`shortCritical` “Crit”/“Hatari”, `shortWatch`, `shortStable`, `shortUnknown` “Unk”/“Haij.”); the Swahili abbreviations and the cluster screen-reader text need native-speaker review.
