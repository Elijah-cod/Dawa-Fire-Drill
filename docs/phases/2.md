# Phase 2 backend notes

Phase 2 is in progress. All inputs are synthetic and all outputs are illustrative and unvalidated. See the later entries below for current capabilities and remaining work.

Next: implement country adapters and reproducible synthetic seed data; persistent, tenant-scoped repositories and migrations; async scenario runs; complete optimization explanations and ranking; funding trace, forecasting, redistribution, capture, provider limits, jobs, authentication, and operational endpoints. Add the required integration and property tests as each module lands.

Initial domain services now also diagnose stalled funding amounts, compute a moving-average reorder point, and filter a transfer by stock, distance, and shelf life. Funding ageing currently uses one supplied record date for all stages; stage-specific timestamps and persistence remain to be implemented. These services are not connected to API routes or real data.

Country configuration includes Kenya and an explicitly rejected `ZZ` placeholder. A reproducible synthetic JSON generator is available; only the facility-level mix is guided by a public aggregate, and all other quantities remain illustrative assumptions as documented in `docs/data-assumptions.md`.

Synthetic datasets are stored as country-scoped immutable seed/version snapshots; scenario runs reuse these inputs. The application-role RLS policies also prevent modifying stored scenario inputs. Superuser and BYPASSRLS roles bypass these protections.

Scenario records now have a country-scoped Postgres repository and Alembic migrations. Idempotency keys are unique per country, and conflicting payloads are rejected.

An authenticated scenario API and a Postgres country policy are now present. Full facility-level authorization still requires review. The app database role must not be a superuser or have BYPASSRLS.

The optimizer now maximizes caller-supplied illustrative benefit, minimizes cost among equally beneficial selections, minimizes unnecessary action count, and uses OR-Tools to order selected actions. Excluded actions receive a budget or optimal-set reason. Benefits are assumptions rather than validated impact estimates; scenario-run integration and a full cut-line explanation remain outstanding.

A first multi-facility scenario calculation uses seeded synthetic records and returns stockouts in deterministic order. Its simplified replenishment assumptions are documented in `docs/data-assumptions.md`. It is not yet asynchronous or persisted.

The Postgres run queue stores country-scoped submissions, supports idempotent creation, and claims work with row locks and expiring lease tokens. An old worker cannot complete a run after a new lease is issued. Authenticated endpoints submit, retrieve, and list runs; a worker processes them and persists illustrative results. Local Compose starts migrations and the worker. An authenticated optimizer endpoint ranks supplied synthetic candidates but does not yet derive them from a scenario run. Finance trace jobs and operations controls still need work.

Synthetic capture now validates uploads, requires caller attestation and facility scope, uses mocked-in-CI OpenAI/Gemini extraction adapters with a shared Postgres call cap and country-scoped cache, and creates stock entries only after explicit human confirmation. Attestation cannot prove image contents are synthetic. Full catalog ingestion, finance jobs, explanation generation, operations controls, and provider behavior against real accounts remain unverified or incomplete.

Funding flows are persisted as immutable, country-scoped records. The trace API computes stage-specific balances and ageing; a repository operation records repeatable dated diagnostics. Forecast and redistribution endpoints accept explicitly attested synthetic inputs. These results are illustrative.

Run `python -m dawa_api.finance_flow.worker --country KE --as-of 2025-01-05` with the backend environment configured to create dated diagnostics and refresh the optional Neo4j projection. Repeating a date does not duplicate Postgres diagnostics; Neo4j uses merge operations. Schedule this command externally for periodic execution. A graph connection failure is reported in its JSON output and does not roll back diagnostics. This projection does not delete obsolete graph records, so clearing an abandoned graph before rebuilding is an operator task. Concurrent graph rebuilds have not been tested.

`/health` reports process liveness; `/ready` checks PostgreSQL and returns HTTP 503 without connection details when unavailable. Neo4j is optional and is not a readiness dependency.

`POST /v1/runs/{id}/mitigations` ranks caller-supplied synthetic emergency procurement, redistribution, and reorder-timing candidates against a completed country-scoped run. Each candidate must target a stockout in that run. Costs and benefit scores are explicit assumptions supplied by the caller; the endpoint does not estimate their effects, derive candidates, or validate feasibility. OR-Tools makes the selection and ordering. This is not yet a complete mitigation model.

HTTP responses include an `X-Request-ID`; the `dawa_api.requests` logger emits a JSON event with method, path, status, duration, and ID when INFO logging is enabled. Headers, request bodies, and query strings are excluded. Avoid putting sensitive values in URL paths.

The forecast service includes a rolling backtest that uses only prior synthetic observations; its tests exercise a generated 24-period history. The replay is illustrative and unvalidated and does not report accuracy metrics. The backtest is not currently exposed as an API endpoint.

Authenticated requests use an atomic Postgres-backed fixed-minute limit per country and hashed subject, shared between API instances. The configured `RATE_LIMIT_PER_MINUTE` applies after token validation; unauthenticated traffic requires a separate edge limit. Each subject retains one counter row, so production deployments need an appropriate retention policy.

The versioned API defaults to `/v1`; `API_PREFIX` changes the prefix when the app is created.

Optimizer responses include a deterministic explanation assembled from the solver result and supplied budget. It cannot alter the selected order. The optional LLM explanation provider remains unimplemented; capture providers do not rank actions.

`GET /v1/runs/compare?left=<run-id>&right=<run-id>` returns two distinct completed runs side by side within the caller's country. Compare their seeds, horizons, scenarios, and assumptions before interpreting differences; results remain illustrative and unvalidated.

Supabase JWT verification accepts legacy HS256 or ES256/RS256 public keys from the configured HTTPS issuer's [JWKS endpoint](https://supabase.com/docs/guides/auth/signing-keys). Signatures, issuer, audience, expiry, and trusted application metadata are checked. The current implementation fetches keys on every asymmetric request; a JWKS outage rejects authentication and adds network latency. Key caching and live-provider testing remain outstanding.
