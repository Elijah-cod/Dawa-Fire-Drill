# Phase 2 backend notes

Phase 2 is in progress. All inputs are synthetic and all outputs are illustrative and unvalidated. Remaining review gaps include public-aggregate calibration beyond facility mix, mitigation effect and feasibility modelling, broader OpenAPI fuzzing, and checks against actual provider accounts. Do not use the current output for operational decisions.

Country configuration includes Kenya and an explicitly rejected `ZZ` placeholder. A reproducible synthetic JSON generator is available; only the facility-level mix is guided by a public aggregate, and all other quantities remain illustrative assumptions as documented in `docs/data-assumptions.md`.

Country-specific synthetic facility validation lives behind an adapter contract, with a Kenya implementation and a non-operational `ZZ` example. Adding another country still requires reviewed configuration, synthetic inputs, and a model adapter; the placeholder is not a real data source.

Unconfigured public-aggregate adapters explicitly fail for demand, lead-time, and funding calibration instead of returning invented data. These adapters are placeholders and are not yet connected to the generator.

Synthetic datasets are stored as country-scoped immutable seed/version snapshots; scenario runs reuse these inputs. The application-role RLS policies also prevent modifying stored scenario inputs. Superuser and BYPASSRLS roles bypass these protections.

`GET /v1/catalog/facilities` and `/v1/catalog/commodities` expose paginated synthetic entries from an existing snapshot, selected by seed and generator version. Planner, pharmacist, and admin roles can read them; a missing snapshot returns 404. The endpoints do not create data as a side effect of a read.

Scenario records now have a country-scoped Postgres repository and Alembic migrations. Idempotency keys are unique per country, and conflicting payloads are rejected.

Authenticated APIs and country-scoped Postgres policies are present. The app database role must not be a superuser or have BYPASSRLS.

The optimizer maximizes caller-supplied illustrative benefit, minimizes cost among equally beneficial selections, minimizes unnecessary action count, and uses OR-Tools to order selected actions. Excluded actions receive a budget, alternative, or optimal-set reason. Benefits are assumptions rather than validated impact estimates; candidate generation and impact modelling remain outstanding.

A multi-facility scenario calculation uses seeded synthetic records and returns stockouts in deterministic order. Its simplified replenishment assumptions are documented in `docs/data-assumptions.md`.

The stock calculation now advances between delivery and depletion events instead of iterating each day. A property test compares it with a simple daily reference, including deliveries and zero demand. The event model retains the same simplifying assumptions and does not model real supply chains.

Simulation version 2 reports the earliest stockout per synthetic district and commodity in addition to facility-level stockouts. The district groupings are invented and do not represent real administrative boundaries. Older stored run results retain their earlier format.

New queued runs pin both generator and simulation versions. The worker supports simulation versions 1 and 2 and fails a run if its pinned version is unavailable. The migration identifies existing version-2 results by their marker and assigns version 1 to unmarked historical or queued runs; their original version cannot otherwise be inferred. Reproducibility across future releases requires retaining each referenced implementation and dataset snapshot.

The Postgres run queue stores country-scoped submissions, supports idempotent creation, and claims work with row locks and expiring lease tokens. An old worker cannot complete a run after a new lease is issued. Authenticated endpoints submit, retrieve, and list runs; a worker processes them and persists illustrative results. Local Compose starts migrations and the worker. The optimizer ranks supplied candidates against a run but does not automatically derive candidates or their effects.

The worker consumes a queue protocol through an injectable factory; the default adapter is PostgreSQL. Scenario and dataset persistence still use PostgreSQL sessions, so a different queue implementation alone would not remove the database dependency.

Synthetic capture validates uploads, requires caller attestation and facility scope, uses mocked-in-CI OpenAI/Gemini extraction adapters with a shared Postgres call cap and country-scoped cache, and creates stock entries only after explicit human confirmation. Attestation cannot prove image contents are synthetic. Provider behavior against real accounts remains unverified.

Funding flows are persisted as immutable, country-scoped records. The trace API computes stage-specific balances and ageing; a repository operation records repeatable dated diagnostics. Forecast and redistribution endpoints accept explicitly attested synthetic inputs. These results are illustrative.

Run `python -m dawa_api.finance_flow.worker --country KE --as-of 2025-01-05` with the backend environment configured to create dated diagnostics and refresh the optional Neo4j projection. Repeating a date does not duplicate Postgres diagnostics; Neo4j uses merge operations and composite uniqueness constraints for flow and stage nodes. The graph role needs permission to create these constraints, or an operator must provision them first. Schedule this command externally for periodic execution. A graph connection failure is reported in its JSON output and does not roll back diagnostics. This projection does not delete obsolete graph records, so clearing an abandoned graph before rebuilding is an operator task. Concurrent graph rebuilds have not been tested.

Graph rebuild tests cover pagination, driver cleanup, constraint setup, and offline fallback; a populated synthetic graph was also checked manually against local Neo4j.

`/health` reports process liveness; `/ready` checks PostgreSQL and returns HTTP 503 without connection details when unavailable. Neo4j is optional and is not a readiness dependency.

`POST /v1/runs/{id}/mitigations` ranks caller-supplied synthetic emergency procurement, redistribution, and reorder-timing candidates against a completed country-scoped run. Each candidate must target a stockout in that run. Candidates targeting the same facility and commodity are treated as mutually exclusive alternatives, so their assumed benefits are not added together; a rejected alternative is identified in the response. Costs and benefit scores are explicit assumptions supplied by the caller; the endpoint does not estimate their effects, derive candidates, or validate feasibility. OR-Tools makes the selection and ordering. This is not yet a complete mitigation model.

Each optimizer solve has a two-second time limit. If any selection or ranking stage cannot prove its optimum, the endpoint returns HTTP 503 instead of returning a partial ranking. Several sequential solver stages may be needed per request.

On 2026-11-06, `python -m dawa_api.simulation.benchmark --seed 42 --iterations 20` on local macOS arm64 with Python 3.12.14 measured a median of 1.387 ms and maximum of 2.794 ms for the in-process simulation over a pre-generated synthetic dataset. This excludes dataset generation, database, queue, and HTTP time; it is a local smoke benchmark, not a capacity guarantee. The scenario output remains illustrative and unvalidated.

On 2026-11-06, Locust 2.47.0 ran `infra/load/locustfile.py` against a local API for 15 seconds with two users. The workload made 22 requests across health, forecast, and optimization, with no failed requests; the slowest response was 92 ms. The test used an ephemeral synthetic planner token and a raised local request limit. This short run is not a capacity or production-readiness claim. To repeat it against a configured local API, set `DAWA_LOAD_TOKEN` to a planner token and run `uvx --from 'locust==2.47.0' locust --headless -f infra/load/locustfile.py --host http://127.0.0.1:8000 -u 2 -r 2 --run-time 15s` from the repository root.

HTTP responses include an `X-Request-ID`; the `dawa_api.requests` logger emits a JSON event with method, path, status, duration, and ID when INFO logging is enabled. Headers, request bodies, and query strings are excluded. Avoid putting sensitive values in URL paths.

The forecast service includes a rolling backtest that uses only prior synthetic observations; its tests exercise a generated 24-period history. The forecast API optionally accepts synthetic stock on hand and estimates the first stockout in the same units as the supplied history periods, assuming constant average demand and no incoming stock. A missing stock value or zero average demand with stock remaining returns no period; zero stock returns period zero. The replay and projection are illustrative and unvalidated and do not report accuracy metrics. The backtest is not currently exposed as an API endpoint.

Authenticated requests use an atomic Postgres-backed fixed-minute limit per country and hashed subject, shared between API instances. The configured `RATE_LIMIT_PER_MINUTE` applies after token validation; unauthenticated traffic requires a separate edge limit. Each subject retains one counter row, so production deployments need an appropriate retention policy.

`POST /v1/redistribution/match` matches one synthetic commodity across supplied sources, targets, and distance lanes. OR-Tools maximizes quantity transferred and then minimizes quantity-weighted distance rounded to the nearest metre, subject to source stock, target need, maximum distance, and minimum remaining shelf life. Results are illustrative suggestions, not physical transfers; the model assumes supplied quantities and distances, does not model route capacity or costs, and presents transfers in identifier order rather than as a priority ranking.

The matcher rejects unknown or duplicate lanes and unavailable solver results. Tests cover role and attestation checks, out-of-range lanes, and sanitized solver failures in addition to stock and need invariants.

The versioned API defaults to `/v1`; `API_PREFIX` changes the prefix when the app is created.

Optimizer responses include a deterministic explanation assembled from the solver result and supplied budget. Set `include_llm_explanation` to opt into an OpenAI/Gemini phrasing request. The provider receives only the optimizer output and must select one of a small set of reviewed sentences; arbitrary prose is rejected. Provider failures or the shared daily call limit fall back to deterministic text. This deliberately limited wording cannot change the selected order. The same Postgres daily call cap is shared with bin-card extraction. No real provider has been tested.

Mitigation identifiers are limited to letters, digits, underscores, and hyphens; they are used in structured results and explanations and are not free-form text.

`GET /v1/runs/compare?left=<run-id>&right=<run-id>` returns two distinct completed runs side by side within the caller's country. Compare their seeds, horizons, scenarios, and assumptions before interpreting differences; results remain illustrative and unvalidated.

Supabase JWT verification accepts legacy HS256 or ES256/RS256 public keys from the configured HTTPS issuer's [JWKS endpoint](https://supabase.com/docs/guides/auth/signing-keys). Signatures, issuer, audience, expiry, and trusted application metadata are checked. Each API instance caches a JWKS response for 60 seconds, coalescing concurrent fetches. During an issuer outage, a cached key works until this local cache expires; after expiry authentication fails closed. A newly rotated key may not be recognized until refresh, and upstream caching may extend key-rotation or revocation delays beyond the local cache lifetime. No live Supabase account has been tested.

Non-superuser PostgreSQL tests cover country isolation for scenario runs, synthetic snapshots, capture cache, funding flows, funding diagnostics, and authenticated request counters. Funding flow snapshots reject updates and deletes for the application role. Production database roles must not be superusers or have `BYPASSRLS`.

Facility-role users can access capture drafts only for the facility in trusted token metadata. Country-wide scenario and run endpoints require planner, pharmacist, or admin access; this prevents a facility user from reading results for other facilities. A facility-specific view of scenario results has not been implemented.

For a local demo, configure `DATABASE_URL` and a valid planner/admin `API_TOKEN` in the environment, start the API, migrations, and scenario worker, then run `scripts/demo.sh` from the repository root. `API_BASE` defaults to `http://localhost:8000`, and `SEED_PYTHON` may point to a Python environment with the backend installed. The script persists a synthetic seed, submits a synthetic shock, polls for the run, and ranks an emergency candidate using explicitly assumed cost and benefit. It stores the token in a private temporary curl configuration and removes that file on exit. The command flow was also exercised against local services using an ephemeral synthetic signing key and token; no real auth credentials were used.

The forecast and standalone optimization endpoints have Schemathesis-generated positive, negative, and authentication contract checks. Duplicate optimization candidate IDs return HTTP 409. This does not yet cover the entire OpenAPI surface.

Synthetic-data attestations and human-review confirmation in JSON requests require the literal Boolean `true`; the capture multipart form uses the text value `true`. The standalone optimizer endpoint now also requires `synthetic_attested: true`. Attestation is a caller statement and cannot verify the actual data or image contents.
