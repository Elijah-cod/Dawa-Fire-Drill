# API documentation

All data must be **synthetic**, with calibration to public aggregates as the target. Facility mix, lead-time anchors, ten tracer demand proxies and an overall funding scale use public aggregates; individual funding stages and temporal patterns remain illustrative assumptions. Model outputs are **illustrative and unvalidated**. See [data assumptions](../data-assumptions.md). Do not publish accuracy claims.

`/health` is public. `/v1/scenarios` supports paginated GET and authenticated POST, and `/v1/scenarios/{id}` supports authenticated GET. POST requires an `Idempotency-Key` header; the same key and payload returns the original record, while a different payload returns 409. Only planner and admin roles can create scenarios. A signed token's trusted `app_metadata` supplies `role` and `country_code`; requests cannot choose a tenant in a header or payload.

The current verifier supports legacy Supabase HS256 JWTs configured with backend-only `SUPABASE_URL` and `SUPABASE_JWT_SECRET`. Asymmetric JWKS verification is not implemented. Missing or invalid configuration fails authentication closed. The Postgres policy requires transaction-local country context. Use a non-superuser application database role without `BYPASSRLS`; Postgres superusers bypass row-level security.

`POST /v1/scenarios/{id}/runs` queues a seeded run with `seed` and `horizon_days` and requires an `Idempotency-Key`. A matching replay returns the existing run; a conflicting replay returns 409. `GET /v1/runs/{id}` returns the country-scoped status and result, and paginated `GET /v1/scenarios/{id}/runs` lists runs for comparison. Results and input data are synthetic; stockout outputs are illustrative and unvalidated.

The worker stores or reuses a country-scoped synthetic snapshot for the run's seed and generator version. Scenario inputs and dataset snapshots are immutable to the non-superuser application role so a completed run can be reproduced. Generate a snapshot explicitly with `python -m dawa_api.ingestion.persist --seed 42 --country KE`; the command prints only a synthetic summary.

`python -m dawa_api.jobs.worker --country KE` polls the Postgres queue; add `--once` to process at most one run. Workers claim rows with a five-minute lease and a fencing token. A failed run exposes a generic error rather than provider or database details. The local Compose stack runs migrations and the worker automatically. It uses disposable local superuser credentials; production must use a restricted application role.

`POST /v1/optimization/rank` accepts synthetic candidate costs, assumed benefits, and an integer budget ceiling from a planner or admin. By default OR-Tools maximizes assumed benefit and minimizes cost among equally beneficial sets. An optional `minimum_benefit` instead selects the least-cost set that meets the supplied score target, breaking cost ties by benefit; an unreachable target returns 409. The same option is available for run-linked mitigations. The response includes the selected order, cut line, remaining budget, and inclusion/exclusion codes. These are illustrative calculations, not validated impact estimates. Candidate benefits and costs are supplied inputs; this endpoint does not yet derive mitigations from a scenario run.

`POST /v1/runs/{id}/modeled-mitigations` accepts synthetic emergency-delivery candidates with an assumed arrival day, quantity and cost. A `reorder_timing` candidate names an existing in-horizon `original_day` and an earlier `arrival_day`; the existing replenishment is moved rather than duplicated. A `redistribution` candidate additionally supplies a donor, available units, dispatch and expiry days, minimum shelf life, and distance limits. Invalid routes are rejected; OR-Tools shares donor inventory across selected transfers and conservatively limits total transfer quantities so the baseline model's donor first-stockout day is not advanced. This limit can reject otherwise feasible combinations, especially at different dispatch days. It replays each candidate against the run's pinned scenario and snapshot, verifies the baseline stockout matches the stored result, and uses modeled days of first-stockout deferral as the OR-Tools benefit. No stockout within the horizon is treated as horizon plus one for this calculation; a delivery after the first stockout cannot undo it. Alternatives for one facility and commodity are mutually exclusive. An optional `minimum_benefit` requests the lowest-cost set reaching that sum of modeled days; costs, actual inventory, routes and timing remain synthetic caller assumptions, and modeled days are not validated impacts.

Because individual effects are replayed independently, the solver also prevents a facility and commodity from simultaneously donating stock and receiving a selected modeled mitigation. This conservative restriction avoids adding effects that would interact; excluded options receive a `donor_recipient_conflict` reason.

`POST /v1/captures` accepts a multipart image, a synthetic demo facility ID, `synthetic_attested=true`, and an `Idempotency-Key`. Only PNG, JPEG, and WebP images within the configured limit are accepted; content is decoded and metadata is stripped before external extraction. The attestation relies on the caller: image content cannot be automatically proven synthetic. Do not submit real stock cards or sensitive data. If configured, the normalized synthetic image is sent to the selected backend-only provider, with fallback to the other configured provider. Failures or the shared daily call cap yield a manual-entry draft. A per-country image-hash cache avoids repeated calls. `GET /v1/captures` lists drafts for a facility with pagination; `GET /v1/captures/{id}` retrieves one. Facility users are restricted to the facility in trusted application metadata.

`POST /v1/captures/{id}/confirm` requires `reviewed: true` and complete corrected fields before a synthetic stock entry is created. Repeating the same confirmation returns the original entry; different values return 409. No original image is retained by this backend. The provider adapters use the [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) and [Gemini structured output API](https://ai.google.dev/gemini-api/docs/generate-content/structured-output); model IDs and keys are configured only on the backend. CI uses mocked HTTP transports and never calls a real provider.

Run `DATABASE_URL=... uv run alembic upgrade head` with a configured backend-only Postgres connection to apply migrations; `uv run alembic downgrade base` reverses the initial migration. Do not commit or print real connection strings.
